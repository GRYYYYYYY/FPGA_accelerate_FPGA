## 语义与覆盖

保留RESERVE/LOOKUP/PIN/MEMORY_DONE/RETIRE/RECYCLE的状态码、固定frame地址、published和四槽租约。辅助桶只存epoch与frame，命中仍读取权威BRAM比较完整owner；published变化不会留下索引副本。索引溢出不会变成物理容量FULL或产生重复owner。

默认32768桶、64次探测、8位epoch，冷启动逐桶清零。epoch正常递增，回绕必须在全表清零后才返回RECYCLE成功。冷启动/回绕清表需32768周期，不能从后续性能预算中省略。原线性目录及原端点源码保持冻结。

| 验证 | 配置与结果 |
|---|---|
| 小容量逐命令差分 | 16 frame、16桶、2次探测、2位epoch；1,460条命令同时与旧目录及独立Python预期结果比较 |
| 回绕和溢出 | 小容量覆盖3次epoch回绕、46次未索引分配、48次空桶后回退；响应背压6,570周期 |
| 默认容量键集合 | 23,405 frame、32K桶、64次探测；最大真实查询的21,883个脏页键，加192个合法对抗键；66,261条命令全部正确 |
| 有界溢出 | 默认容量测试75次未索引分配，后续LOOKUP及重复RESERVE保留正确frame；42次空桶回退 |
| 故障注入 | 移除耗尽后的扫描、忽略owner命名空间、索引命中返回错误published、回绕清表前提前响应，四项均由预期检查检出 |

真实键源是全部38查询集合实验中最大的查询（attempt 543648），按首次写入页顺序分配，再逆序LOOKUP与重复RESERVE。对抗集合来自此前同query/price的低负载碰撞控制。这里验证owner映射，**并非按原始14,047,736次字段访问执行LRU、checkpoint或AXI传输**。大容量测试仅使用独立命令oracle，没有运行线性目录RTL；原始TB日志中的`ref_cycles`是禁用参考实例时的镜像，最终manifest已将其置为null，不能用来比较性能。

## 周期与综合

小容量压力测试累计命令接受至响应可见的周期：索引15,910，线性15,622，索引多288周期（约1.84%）。两者均另有相同的外部响应背压；索引初始16周期清表不包含在命令延迟之和内，命令触发的回绕清表包含在内。这个负收益说明小表与高碰撞下不能预设哈希更快。

默认容量集合测试的索引累计命令延迟946,545周期，另有32,768周期初始清表、298,173周期响应背压。没有同流量线性RTL对照，因此不报告大容量加速比。以上均为行为仿真周期，不是实卡耗时。

Vivado 2022.2、U280、默认容量的独立目录综合：

| 资源 | 线性目录 | 索引目录 | 增量 |
|---|---:|---:|---:|
| LUT | 480 | 747 | +267 |
| FF | 500 | 606 | +106 |
| RAMB36 | 18 | 39 | +21 |
| DSP | 0 | 3 | +3 |
| latch | 0 | 0 | 0 |

这些是目录模块资源，不能当作完整端点总量。mixed32乘法被映射到3个DSP。综合报告的预布局建立裕量为+5.533/+5.496ns，但111输入/62输出没有接口延迟、缺少HD.CLK_SRC，且尚未布局布线；不能据此宣布频率闭合。所有警告保留。
